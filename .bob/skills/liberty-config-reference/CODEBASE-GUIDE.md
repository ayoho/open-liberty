# Codebase Guide: `liberty-config-reference`

> **Purpose**: Architectural context for Liberty's configuration reference — how configuration elements are defined, how metatype drives the schema, and where to find source of truth for any configuration element. This guide is intentionally concise; the SKILL.md contains the authoritative attribute reference. This guide explains the *system* behind the reference. Complements the user-facing SKILL.md.
>
> All paths are relative to `dev/` inside the Open Liberty repository root.

---

## 1. Domain Overview

Liberty's configuration reference is not a static document — it is **generated from metatype.xml files** in each bundle. Every configurable element (`<dataSource>`, `<httpEndpoint>`, `<ldapRegistry>`, etc.) is defined by an ObjectClassDefinition (OCD) in a bundle's metatype. The full schema for `server.xml` is the union of all metatype OCDs from all installed features. Understanding the metatype system is essential for understanding why configuration elements exist, what their defaults are, and how to extend them.

**Key bundle**:
| Bundle | Role |
|--------|------|
| `com.ibm.ws.config` | Config Admin, metatype registry, schema generation |
| Each feature bundle | Ships `resources/OSGI-INF/metatype/metatype.xml` defining its elements |

## 2. Metatype as the Schema Source

### 2.1 OCD → server.xml Element Mapping

Every `server.xml` element corresponds to one ObjectClassDefinition in a metatype.xml. The mapping:

```
metatype.xml OCD (id="httpEndpoint")
    ↓ (ibm:alias="httpEndpoint")
<httpEndpoint> in server.xml
    ↓ (via ConfigAdmin)
HttpEndpointImpl @Activate(Map<String,Object> config)
```

The `ibm:alias` attribute on the OCD's `Designate` element provides the short XML element name. Without it, users would write the full PID as the element name.

### 2.2 Attribute Types and Defaults

Each `AD` (AttributeDefinition) in the OCD declares:
- `id` → server.xml attribute name (camelCase)
- `type` → Java type (String, Integer, Boolean, Long, Duration, etc.)
- `default` → value used when not specified in server.xml
- `required` → whether the attribute must be provided
- `ibm:type` → Liberty extension for reference types (`pid`, `duration`, `password`)

**`ibm:type="duration"`**: Duration attributes (e.g., `connectionTimeout="10s"`) accept values like `10s`, `500ms`, `2m`. The `MetaTypeRegistry` converts these to milliseconds before delivering to the component.

**`ibm:type="password"`**: Password attributes accept encoded values (`{xor}...`, `{aes}...`). Liberty decodes them before delivering to the component. Plain text is also accepted but warns.

**`ibm:type="pid"`**: Reference attributes (e.g., `<dataSource jdbcDriverRef="myDriver"/>`) use `ibm:type="pid"` with `ibm:reference` pointing to the referenced element's PID. Config Admin resolves the reference and delivers the referenced configuration's values as a nested `Map`.

**`ibm:type="token"`**: Special type for single-use tokens (used in password attributes before `{xor}` encoding is applied). Ensures the value is not logged in trace.

**Nested configuration elements**: When a `server.xml` element has child elements (e.g., `<dataSource><jdbcDriver .../></dataSource>`), the child element is either a nested factory PID (creates a new configuration with a generated PID) or an `ibm:childAlias` reference. The parent component receives the child's PID in its configuration map. This allows hierarchical configuration without requiring top-level JNDI names for sub-elements.

### 2.3 Schema Generation

The full `server.xml` schema XSD is generated by the `configUtil` command (or as a build step) by scanning all installed metatype files and synthesising an XSD. IDE tooling (VS Code Liberty Tools, Eclipse DevTools) uses this generated schema for autocompletion and validation.

**Finding the metatype for any element**:
```bash
# Find metatype for <httpEndpoint>:
grep -r "httpEndpoint" dev/com.ibm.ws.transport.http/resources/OSGI-INF/metatype/
# or for any element:
grep -r "ibm:alias=\"<elementName>\"" dev/*/resources/OSGI-INF/metatype/metatype.xml
```

### 2.4 IBM-SPI-Package and API Exposure in Metatype

Feature manifests declare which packages are API vs. SPI using `IBM-API-Package` and `IBM-SPI-Package` headers. The metatype system uses a similar concept: OCD elements tagged with `ibm:api-type="stable"` (or `"beta"`) are included in the public schema XSD; OCD elements tagged with `ibm:api-type="internal"` are not exposed in the schema. This controls which config elements appear in IDE autocomplete and the published documentation.

### 2.5 Configuration Reference Documentation Generation

Liberty generates its online configuration reference documentation from metatype files plus human-readable descriptions in the `AD description` attribute. The documentation build pipeline:
1. Scans all feature bundles for metatype XML
2. Extracts `OCD name`, `AD description`, `AD default`, `AD required` for each element
3. Generates the HTML documentation at `https://www.ibm.com/docs/en/was-liberty`

This means the most accurate and up-to-date documentation for any config attribute is in the bundle's metatype.xml `AD description`.

## 3. Key Entry Points

### 3.1 Config Schema Infrastructure

| Class / File | Path | What to look for |
|-------|------|------------------|
| `MetaTypeRegistry` | `com.ibm.ws.config/src/com/ibm/ws/config/xml/internal/MetaTypeRegistry.java` | Loads all metatype; merges defaults with server.xml values |
| `ExtendedMetatypeManager` | `com.ibm.ws.config/src/com/ibm/ws/config/xml/internal/ExtendedMetatypeManager.java` | IBM-specific metatype extensions (ibm:alias, ibm:type, ibm:flat, ibm:childAlias) |

### 3.2 Representative Metatype Examples

| Metatype File | Path | What to look for |
|-------|------|------------------|
| HTTP endpoint | `com.ibm.ws.transport.http/resources/OSGI-INF/metatype/metatype.xml` | Full metatype for `<httpEndpoint>`, `<httpOptions>`, `<tcpOptions>`; shows nested child alias pattern |
| DataSource | `com.ibm.ws.jdbc/resources/OSGI-INF/metatype/metatype.xml` | `<dataSource>`, `<jdbcDriver>`, vendor `<properties.*>` elements; shows factory PID pattern |
| Security | `com.ibm.ws.security.authentication.builtin/resources/OSGI-INF/metatype/metatype.xml` | Auth cache configuration; shows singleton PID with optional config |
| Logging | `com.ibm.ws.logging/resources/OSGI-INF/metatype/metatype.xml` | `<logging>` element; shows ibm:type=duration and ibm:type=token examples |

### 3.3 Configuration Validation

Liberty validates `server.xml` against metatype at startup. Validation errors are logged as `CWWKG0032W` (unrecognised attribute) or `CWWKG0074W` (invalid attribute value). The `configUtil schemaGen` command generates the full XSD from installed metatypes:
```bash
bin/server schemaGen myServer --outputType=xsd --output=liberty-schema.xsd
```
This generated XSD can be used for pre-deployment config validation in CI/CD pipelines.

## 4. Design Decisions & Gotchas

**Q: How do you discover what configuration attributes an element supports beyond what is documented?**
A: Read the bundle's metatype.xml directly. For `<dataSource>`, find it at `com.ibm.ws.jdbc/resources/OSGI-INF/metatype/metatype.xml`. Every `AD` element is a valid attribute. Attributes marked `required="true"` must be provided; all others have defaults. The `ibm:variable="..."` attribute allows the default value to be an expression resolved at runtime.

**Q: Why are there so many `<properties.xxx>` sub-elements for JDBC vendors?**
A: Each JDBC vendor has driver-specific properties (database name, server name, port, etc.) that differ from vendor to vendor. Rather than a single `<properties>` element with all possible vendor properties, Liberty generates a separate OCD per vendor via a metatype extension mechanism. This provides type-safe, validated, documented properties per vendor. The downside is that switching database vendors requires changing the element name.

**Q: How do I find the default value for a configuration attribute?**  
A: Read the bundle's metatype.xml — the `AD` element's `default` attribute is the source of truth. Alternatively, use `configUtil --outputType=minifyXSD` to see the generated schema with defaults annotated.

**Q: What does `ibm:type="duration"` do with `0` as a value?**
A: `0` (or `0s`) means zero duration. Some attributes interpret this as "disabled" (e.g., `connectionTimeout="0"` disables connection wait timeout). Others treat it literally as 0ms. Read the metatype `description` attribute for the specific element to understand zero semantics.

**Q: What is an `ibm:childAlias` and how does it differ from a nested factory PID?**
A: An `ibm:childAlias` allows a child element to be referenced by alias within its parent, rather than requiring a separate top-level declaration. For example, `<jmsConnectionFactory><properties.wasJms/></jmsConnectionFactory>` — the `<properties.wasJms>` is a child alias, not a standalone factory element. The parent receives the child's properties directly in its `Map`, rather than as a PID reference. This simplifies configuration for tightly-coupled parent/child relationships.

**Q: What is the difference between `ibm:flat="true"` and nested child OCD in metatype?**
A: `ibm:flat="true"` causes a child element's attributes to be merged into the parent element's flat `Map` rather than delivered as a nested `Map`. Used for tightly-coupled sub-elements where the component expects all properties in a single map (e.g., `<tcpOptions>` inside `<httpEndpoint>`). Without `ibm:flat="true"`, the child appears as a nested `Dictionary` under its PID key.

## 5. How to Update This Guide

- **New config elements**: Every new feature adds metatype; this guide covers the system, not individual elements. Update SKILL.md for new element documentation.
- **New `ibm:type` values**: If new Liberty-specific attribute types are added to the metatype extension, update §2.2.
- **Schema generation tool changes**: If `configUtil` is replaced or extended, update §2.3.
- **Verification**:
  ```bash
  find dev -name "MetaTypeRegistry.java" -path "*/src/*"
  find dev -name "metatype.xml" -path "*/OSGI-INF/metatype/*" | wc -l
  ```
